I am building a C# security assessment utility and local web demo framework that combines a modular CLI shell, an asynchronous HttpListener-based file server, template injection logic, tunnel provisioning, and a live location/metric dashboard. The project is currently in a transitional state: it compiles, the test suite passes, and core HTTP serving and command-driven module behavior are implemented, but the system is not yet a complete end-to-end operational exploit/demo flow. I need you to understand the current project as a functional prototype with a clear skeleton for production-like expansion.

PROJECT ARCHITECTURE
This project is organized into a small, layered application structure centered around an executable entry point and a modular console host:

Program entry: Program.Main in the root namespace launches the app and catches fatal exceptions.
CLI and host layer:
ConsoleUI handles banner, prompts, status, and basic console formatting.
CommandLine.Parse/PrintHelp handles startup flags such as template, port, tunnel, help, and banner skipping.
CommandModuleRegistry manages module lookup and execution.
IConsoleModule defines the standard interface for dynamic modules.
InteractiveConsoleHost provides the interactive command loop, configuration state, help, load/run/stop flow, and direct command execution.
DemoModule is the concrete module that spins up the demo lifecycle.
CommandExecutionResult is the structured result object used by modules and the console.
Core orchestration:
Coordinator.RunAsync executes the main one-shot workflow: detect platform, prepare template, inject script/UI into HTML, save output, start web server, optionally start tunnel, save session snapshot.
CoreHelper.ParseAndFormatLocationAsync is a console-driven metric formatter with ANSI purple/magenta dashboard output.
SessionLogger.SaveAsync persists session metadata to JSON.
File generation/injection:
HtmlProcessor.InjectGeolocation injects a browser geolocation script and consent-driven UI into an HTML document before the closing body tag.
FileInjectionUtility.InjectBeforeLocator injects raw text before a specified locator string while preserving encoding and handling larger files safely.
TemplateInjector and GeneratedSite are present but empty, indicating planned future scaffolding rather than active implementation.
HTTP serving:
WebServer is the main local file server. It uses HttpListener with an asynchronous accept loop and Task.Run handling to serve concurrent requests.
It supports static files, route mapping, a /log endpoint, and /api/ip-location.
Routes.cs defines route metadata with RouteInfo and IsApiRoute, but the route system remains a basic support layer rather than a full routing engine.
Tunnel logic:
ITunnelProvider defines provider contract.
NgrokProvider and CloudflareProvider implement actual tunnel startup logic.
TunnelManager.StartAsync decides which provider to use.
Geolocation and data model:
IpGeolocation.GetLocationAsync resolves IP-to-location data.
DeviceLocation and LocationResult model geolocation outputs.
LocationComparer calculates coordinate distance.
Platform detection:
PlatformDetector.Detect and PlatformInfo provide environment detection.
Dependencies:
DependencyManager, DependencyManifest, BinaryVerifier, Downloader are present but not central to the active request flow and likely represent a dependency bootstrap strategy.
FUNCTIONAL CORE
The core data flow is intended to work like this:

The HTML template or generated page is created using the default template or a custom file path.
HtmlProcessor.InjectGeolocation takes HTML, injects a consent-driven geolocation script and helper UI, and appends that block before the closing body tag.
WebServer serves the generated HTML from a local directory using HttpListener. It also supports route mapping via MapRoute, where a URL path like /it-check or /hr-portal resolves to a specific directory.
The injected JavaScript executes in the browser. It queries /api/ip-location to retrieve coarse IP-derived location data, then uses navigator.geolocation if the user grants permission.
The resulting browser coordinates, metadata, and triggering context are intended to be sent to a listener or logging endpoint.
WebServer.HandleRequestAsync routes /api/ip-location to HandleIpLocation and /log to HandleLog.
HandleIpLocation queries IpGeolocation.GetLocationAsync to get location data from the client remote IP address and serializes the result as JSON.
HandleLog parses NameValueCollection query parameters and returns them as JSON, demonstrating the parsing model for incoming query strings.
CoreHelper.ParseAndFormatLocationAsync formats the final parsed data into a purple/magenta ANSI dashboard. It takes clientIp, browserLat, and browserLon strings and prints:
an estimated IP-based location metric block
a precise hardware location block if browser coordinates are present
a yellow warning if browser coordinates are omitted
The tunnel layer is designed to expose the local application via ngrok or Cloudflare, so a remote client or external evaluator can access the generated page without exposing the local machine directly.
The intended full data path is:
HTML/JS payload -> browser execution -> outbound HTTP request -> tunnel -> local HttpListener -> WebServer request handlers -> IpGeolocation and query parsing -> CoreHelper dashboard formatting -> console output.
This is the conceptual flow that the project is trying to implement. In the current state, it is partially realized but not fully connected into a complete end-to-end exploit scenario.

METRIC THEME
The active console output theme is a stylized purple/magenta terminal dashboard built into CoreHelper.ParseAndFormatLocationAsync. The color palette is defined using ANSI escapes:

Primary Accent: deep purple / magenta = \x1b[35m
Secondary Accent: bright purple / pink = \x1b[95m
Success Status: cyan / green = \x1b[36m
Warning / Alert: yellow = \x1b[33m
Reset: \x1b[0m
The dashboard format is intentionally visual and designed to look like a telemetry block:

header banner: “=== PROXIED METRIC STREAM ===”
deep purple bordered data frame
“Location Metric Type A (Estimated IP)” label
IP address shown in white
generated Google Maps query URL rendered in bright purple
“Location Metric Type B (Accurate Hardware)” section in cyan when browser coordinates are available
yellow warning indicator when browserLat and browserLon are missing: “[!] Precise hardware boundary coordinates omitted by client.”
final deep purple footer border closes the block cleanly
console is explicitly reset to default at the end of execution
This is a strong terminal visualization layer, but it is currently a presentation shell rather than a fully integrated runtime telemetry dashboard fed by the actual browser and tunnel pipeline.
